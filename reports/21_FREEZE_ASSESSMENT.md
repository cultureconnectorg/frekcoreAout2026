## The exact remaining blockers (only these)

1. **No real-MongoDB validation of anything in any Phase 3 report.** Everything runs through a documented `mongomock_motor` substitute. Gates confident answers on almost every other row above. **Execution-ready plan prepared, not yet run**: `reports/23_REAL_MONGODB_VALIDATION_PLAN.md` — environment requirements, exact commands, expected test set (528 tests as of this pass, re-count at execution time), and specific index/uniqueness/atomicity/concurrency/persistence checks with rollback/cleanup steps. Per founder directive §18, the specific guarantees this blocks (indexes, uniqueness, atomicity, concurrency, transactions) remain classified `BLOCKED / UNVERIFIED_REAL_MONGO`, not proven-correct or proven-broken, until that plan is actually executed and its results recorded back into that same report.
2. **CLOSED** (`reports/22_P0_SECURITY_CLOSURE.md`, then hardened further `reports/FREKCORE_COMPLETION_BACKLOG.md` P1 #3): the unauthenticated-mutation blocker is resolved, and the interim admin-key-only gate has since been replaced with real per-holder authorization for `fingerprint`/`geo` consent and sensitive reads (`identity_engine`'s `X-FREK-Session`, admin key as override only) — no longer a "narrower gap," fully closed for these routes. `fingerprint`'s `/match` remains deliberately admin-only (cross-subject, documented reasoning, not a gap).
3. **Dual identity system (C1)** — founder-resolved as "reconcile, don't replace" (`docs/decisions/0001-...`), capability-ownership mapped (`docs/architecture/FREK_ID_RECONCILIATION.md`), and now proven live twice over (the fingerprint/geo per-holder-auth fix, `registry/`'s write-authority check both use the map's own recommended cross-system `linked_objects` pattern). The specific question of same-system merge vs. permanent separation is the subject of `docs/decisions/0002-identity-lifecycle-founder-decisions-needed.md` §1, awaiting founder decision. **`backend/frek/`'s fate (C4)** — founder-resolved as "not deletable, not globally deprecated, under reconciliation"; all 43 routes now individually classified (`docs/architecture/FREK_LEGACY_ROUTE_AUDIT.md`, corrected route count and disposition table, both from stale earlier arithmetic) — 19 of 43 still need founder input on a route-by-route basis (all sharing one root cause: the module's real storage backend is structurally non-persistent, see below).
4. **`backend/frek/`'s core storage** (NODE04 Memory, NODE06 Réseau) is built for PostgreSQL+`pgvector` and reads `MONGO_URL` to decide whether to activate it — a MongoDB-named variable that never starts with `postgres` anywhere in this codebase's actual configuration, so the real backend is structurally unreachable and every write silently falls back to non-persistent in-process memory (`docs/architecture/FREK_LEGACY_ROUTE_AUDIT.md`). This is a genuine capability gap, not a security issue: a client calling `POST /frek/certify` reasonably expects the result to be retrievable later, and today it is not, past a restart.
5. **Contradiction C6**: the canonical architecture spec (`frek_v3/docs/FREK_Architecture_Integree_v0.2.md`) calls for typed `did:frek:{person,org,device,app}-<uuid>` identifiers; `backend/did/document.py` implements an untyped `did:frek:{frek_id}` — no code consumes type discrimination today, so this is not urgent, but should be resolved before any hardware-capture (Luciole/FAP) work begins, since that work's own spec assumes it. See `docs/architecture/FREK_ID_CANONICAL_MODEL.md` §4.
6. **`identity_engine` merge/renew/recovery** — founder decision needed, package prepared: `docs/decisions/0002-identity-lifecycle-founder-decisions-needed.md`. Notably, `recovery` is not a hypothetical gap: today, a holder who loses every registered Passkey has zero mitigation, not even an admin escape hatch — the package's recommended option (an admin-key override on `register_begin`/`register_complete`, mirroring this module's own established `_holder_or_admin` pattern) closes this but is not implemented pending sign-off.
7. **115 known dependency vulnerabilities**, not bumped beyond the one required to fix the install blocker (needs green integration suite against real MongoDB first to bump safely — see blocker #1).
8. **Docker Compose / container build never executed end-to-end** in this environment (network-policy blocked).
9. **Two mission briefs received but not executed**: Red/Blue/Purple Team security assessment, UI/UX/SPA/Motion/3D/Accessibility overhaul — both independently multi-week-scale (see closing note). Per founder directive §26-27, both are scheduled *after* the P0/P1 trust baseline is stable, which is directionally where this pass leaves things, not yet fully there.
