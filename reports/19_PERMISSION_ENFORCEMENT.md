# 19 — Permission Enforcement (Phase 3, Priorities 4 & 5)

## Priority 4 — Permission Matrix (audit before wiring)

Done in full: `docs/PERMISSION_MATRIX.md`. Methodology: automated extraction of all 239 pre-Phase-3 routes (regex over `@*_router.get/post/put/patch/delete(...)` decorators across every mounted router), automated detection of known `Depends(...)` auth patterns plus header-check patterns, then a manual spot-check of the 43 routes the automated pass could not attribute a category to.

Category outcome, in one line: **PUBLIC / PUBLIC-SECRET / AUTHENTICATED / OWNER-SCOPED / ADMIN / SYSTEM-AGENT / INTERNAL are all real, in-use categories in this codebase. ORGANIZATION-SCOPED is not implemented anywhere** — confirmed by grep, no route conditions access on an organization/tenant field. Any future multi-tenant CVLN integration (Wallet, KORA, Academy as separate *organizations* rather than separate OAuth2 clients) has no existing enforcement primitive to build on; this is a real gap, recorded as `docs/PERMISSION_MATRIX.md`'s category-definitions section.

The matrix's own "FLAG — genuine findings" table names the remaining gaps: fingerprint consent/observe/match routes, geo consent/observe/notarize/encode routes, `POST /api/core/count`, `POST /api/v1/checkout`. **Correction, made after this report was first written**: `POST /api/v1/notary/notarize` and `/anchor/*` were originally listed here too — re-reading `backend/notary/routes.py` found they already carry real `Depends(require_permission("emit"))` enforcement (live-verified: `test_anchor_sweep_requires_auth` passes in every integration run). See `docs/PERMISSION_MATRIX.md`'s correction note for the root cause of the original miss (the automated scan didn't recognize a `Depends(require_permission(...))`-style wrapper call as an auth pattern) — the same re-check also cleared `sync_router`, `heritage_router`, and `pdf_batch_router`'s previously "not fully audited" routes as genuinely protected.

## Priority 5 — What this phase actually wired

**Audit Trail**: wired for exactly one event this phase — `identity.created` (`backend/server.py`'s `_audit_trail_startup()`, subscribing `make_audit_trail_subscriber(_audit_recorder)` to `default_bus` on that event type). Every field the mission required is present on the resulting `AuditEvent`: `actor_frek_id`, `correlation_id`, `timestamp`, `action`, `resource_type`, `resource_id`, `result`, `metadata` (carrying `event_id` and the event payload) — see `backend/audit_trail/subscribers.py:event_envelope_to_audit_event`. No secret is ever placed in `metadata`: the mapped payload comes from `identity_engine`'s existing `identity.created` event envelope, which itself never carries a raw credential (verified by reading `identity_engine/service.py`'s event-emission call site — it publishes `frek_id`, `created_at`, not the WebAuthn credential).

Verified live this phase (mongomock-backed real server): creating an identity via `POST /api/v1/identity/init` produces exactly one new document in `audit_trail_events` with `action="identity.created"`, `result="success"`, and a `correlation_id` matching the request's `X-Correlation-ID`/`X-Request-ID` header (Priority 7's middleware). 4 unit tests cover the subscriber in isolation (`backend/tests/test_audit_trail_subscribers.py`), exercising the success path, the "record raises" path (logged, not propagated — a broken audit write must never break the triggering request), and the "no running event loop" path.

**Not wired this phase, and why**: no enforcement was added to any of the FLAG routes in `docs/PERMISSION_MATRIX.md`. Reason: this phase's real-application evidence came from a `mongomock`-backed server (`reports/16_INTEGRATION_TEST_BASELINE.md` §1), not a real MongoDB — adding an auth dependency to a previously-unauthenticated route and regression-testing it only against `mongomock` risks a false-positive "it works" that a real MongoDB's index/constraint behavior could contradict. Wiring enforcement on routes this session cannot fully regression-test violates the mission's own "preserve backward compatibility, verify before changing" instruction more than leaving the gap documented does. This is `reports/FREKCORE_COMPLETION_BACKLOG.md` P0 #1 — first in line once P1 #1 (real MongoDB) is available.

**Permissions Engine model status, unchanged from Phase 2**: `backend/permissions/` (Role/Scope model, `PermissionChecker`) exists, is unit-tested, and is **not** imported by `backend/server.py` or any route module (`grep -rn "from permissions" backend --include="*.py" | grep -v tests/permissions/` → no matches outside the module's own package). It remains a validated-in-isolation model, not an enforcement mechanism — same finding as Phase 2, re-confirmed this phase.

## Bottom line for the Freeze Criteria (see `reports/21_FREEZE_ASSESSMENT.md`)

**Permissions: PARTIAL** (matrix built and accurate, model exists and is tested, zero routes gained new enforcement this phase). **Audit Trail: PARTIAL** (real, live-verified, MongoDB-backed writes — but scoped to one event type out of the mission's five-item list: identity creation/update/revoke, proof generation, certificate issuance, admin mutation, permission denial. Only identity creation is wired; update/revoke don't exist yet as `identity_engine` capabilities (Contradiction C1), proof generation and certificate issuance have no existing event producer to subscribe to, admin mutation and permission denial were not in this phase's Priority 5 scope beyond the identity-creation wiring already done).
