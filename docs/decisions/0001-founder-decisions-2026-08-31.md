# ADR 0001 — Founder Decisions & Canonical Reconciliation Directive (2026-08-31)

**Status**: ACCEPTED — authoritative, overrides any prior session recommendation that would reduce, replace, reinterpret, or delete the historical FREK vision.

**Source**: "FREKCORE — FOUNDER DECISIONS + CANONICAL RECONCILIATION MASTER DIRECTIVE", received on branch `claude/frekcore-v1-production-b9h2q0` at validation head `df1b577`, immediately after the "CLOSE THE LOOP" validation pass concluded with `NOT READY FOR FREEZE`.

## Why this ADR exists

Per this directive's own §30 (Source of Truth Priority), explicit founder decisions outrank current code behavior and newer-implementation convenience. This document is the durable record of those decisions, so no future session (or this one, later) treats a prior "the newer module supersedes the old one" reading as settled when the founder has explicitly said otherwise.

## Decisions recorded (condensed; §§ refer to the full directive)

1. **§1 — FREK-ID is the canonical concept**, not any one technical implementation. `identity_engine == FREK-ID` and `frek_v1 == obsolete FREK-ID` are both rejected as unevidenced equivalences. Multiple technical subsystems may express different parts of one FREK-ID vision; they are reconciled, not collapsed by assumption.
2. **§2 — `identity_engine` is a modern technical identity engine**, not FREK-ID itself. WebAuthn/Passkey are authentication mechanisms a FREK-ID may use; they are not the identity. This distinction is preserved in all architecture and documentation going forward.
3. **§3–4 — The historical lifecycle (GENESIS → WORKSHOP → METAMORPHOSE → EMISSION → LEGACY) is not obsolete by default.** Its semantics must be reconstructed from documentation and code before any relocation decision. See `docs/architecture/FREK_ID_CANONICAL_MODEL.md`.
4. **§5 — Contradiction C1 (`reports/FREKCORE_CONTRADICTIONS.md`) is resolved as: reconcile, do not replace.** One coherent FREK-ID trust model, multiple subsystems underneath it, mapped via `docs/architecture/FREK_ID_RECONCILIATION.md`. No silent collection merges, no identity deletion, no FREK-ID regeneration, no blind production-data migration.
5. **§6 — Target a single canonical FREK-ID resolution interface** for external CVLN consumers, contract-first, backward-compatible. Not implemented blindly this session — documented as a target in the reconciliation doc.
6. **§7 — Missing `identity_engine` lifecycle endpoints** (revoke/update/archive/renew/recovery) are not to be copied verbatim from `frek_v1`. Semantic equivalence must be checked per-operation first.
7. **§8 — DID/VC/EUDI/OpenID4VCI/OpenID4VP/SD-JWT are interoperability mechanisms around FREK-ID, never a replacement for it.** No compatibility claims without implementation evidence (unchanged from the existing rule already in force this session).
8. **§9 — Contradiction C4 (`backend/frek/`) is resolved as: NOT authorized for deletion, NOT globally deprecated.** Reclassified from "legacy, largely unaudited" to **"HISTORICAL FREK — UNDER RECONCILIATION"**. Full per-route audit required before any route-level decision — see `docs/architecture/FREK_LEGACY_ROUTE_AUDIT.md`.
9. **§11 — Route reconciliation classification vocabulary** (PRESERVE / HARDEN / ABSORB / MIGRATE / ADAPTER / SUPERSEDE / DEPRECATE / NEEDS_FOUNDER_DECISION) replaces the earlier binary "legacy vs. current" framing for `backend/frek/`'s 33 routes. Never classified by file age alone.
10. **§12 — FREK terminology (GENESIS, WORKSHOP, METAMORPHOSE, EMISSION, LEGACY, RESONANCE, TRANSMISSION, etc.) is preserved as potential conceptual IP**, not normalized to generic SaaS vocabulary for developer convenience.
11. **§13 — C5 (the FastAPI template scaffold `/api/status`) may be deprecated/removed** once verified to have no real consumer, no documentation defining it as a FREK capability, and no integration dependency — distinct from FREK IP, safe to clean up once verified.
12. **§18 — The Run 4 integration baseline's 29 failed / 39 errored items, gathered against `mongomock`, are not proof of real-MongoDB-specific defects and are not proof of real-MongoDB-specific correctness either.** Reclassified as `BLOCKED / UNVERIFIED_REAL_MONGO` for the specific guarantees that depend on real MongoDB semantics (indexes, uniqueness, atomicity, concurrency, transactions), pending a real MongoDB environment this sandbox cannot reach.
13. **§21–22, §26–27, §31 — Execution order is fixed**: founder-decision ADR (this document) → P0 security gaps → 33-route historical audit → canonical FREK-ID model + reconciliation → present remaining genuine contradictions → P1 backlog → real-Mongo validation → dependency remediation → Red/Blue/Purple security mission → remediation → UI/UX mission → final validation → matrix update → freeze assessment. Later steps are not to be started, still less claimed complete, ahead of earlier ones without cause.
14. **§28 — Autonomy boundary.** Bug fixes, tests, route hardening, validation improvements, confirmed dead/template-code removal, documentation reconciliation, and already-decided missing-capability implementation may proceed without further sign-off. Anything that would remove a historical FREK concept, redefine FREK-ID, break an existing identifier, merge incompatible identity semantics, change `.fk` semantics, remove a proof mechanism, remove lifecycle semantics, change economic/legal meaning, create an incompatible public API, or permanently delete historical data stops for a founder decision.
15. **§32–33 — Definition of completion and freeze condition restated**: FREKCORE is complete when every intended capability has an explicit, truthful outcome (VERIFIED, or explicitly SUPERSEDED/DEPRECATED/REJECTED with justification) — not when every historical line of code survives untouched, and not by silent disappearance either.
