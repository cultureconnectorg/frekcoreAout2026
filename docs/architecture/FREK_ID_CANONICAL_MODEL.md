# FREK-ID Canonical Model

Per founder directive §3 (`docs/decisions/0001-founder-decisions-2026-08-31.md`): reconstructs the FREK-ID semantic model from documentation and code, distinguishing **CONCEPT** (what the founder's own architecture documents say FREK-ID is meant to be) from **IMPLEMENTATION** (what the code actually does today) — per §30's source-of-truth order, explicit founder decisions first, then canonical historical FREK specifications, then validated current architecture, then code behavior, and newer code never silently redefines the vision.

This is a first-pass reconstruction (same honesty standard as `reports/FREKCORE_MASTER_REQUIREMENTS_MATRIX.md`'s own "Scope note") — it covers every source this session found that speaks to FREK-ID's meaning, not a claim of having read every historical document line-by-line.

## 1. CONCEPT — what the canonical specification says FREK-ID is

**Primary source**: `frek_v3/docs/FREK_Architecture_Integree_v0.2.md`, self-labeled `Statut: ARCHITECTURE VALIDÉE` — the most authoritative FREK-ID specification this session found, and the newest by date (2026-08-10). Its own closing statement: *"FREK-ID = identité universelle."*

- **FREK-ID is a `did:frek:<id>` — a W3C DID (Decentralized Identifier), not an internal database key.** It resolves to a real DID Document (`@context`, `verificationMethod` with an Ed25519 public key, `assertionMethod`, `authentication`).
- **FREK-ID has four typed subject kinds**, each with its own ID prefix convention: `did:frek:person-<uuid>` (a person), `did:frek:org-<uuid>` (an organization), `did:frek:device-<uuid>` (a physical device — e.g. a Luciole capture unit), `did:frek:app-<uuid>` (an application/service).
- **FREK-ID is the anchor a Verifiable Credential is issued *by* or *about*** — the spec's own worked examples: `did:frek:laurentia-001` issues a `FREKAuthorshipCredential` ("J'ai créé cette œuvre"); `did:frek:device-luciole-001` issues a `FREKCaptureCredential` (hardware-signed capture attestation, PUF-derived key, `captureTimestamp`/`audioFingerprint`/`firmwareVersion`/`counter` claims).
- **FREK-ID is not itself authentication.** The spec's pipeline separates *identity* (a DID that can be resolved and whose claims can be verified) from the *authentication event* that lets an actor act as that DID (in the spec, hardware Ed25519 signing for a device; for a person, the spec does not specify a mechanism — this is the gap `identity_engine`'s WebAuthn work fills, but WebAuthn is the *authentication mechanism*, not a redefinition of what the DID means). This exactly matches founder directive §2's instruction: "WebAuthn is NOT FREK-ID. Passkey is NOT FREK-ID. Authentication is NOT identity."
- **FREK-ID is meant to be interoperable, not proprietary**: the spec explicitly targets W3C DID Core, W3C VC Data Model 2.0, Ed25519Signature2020, SD-JWT VC, OID4VCI, EUDI Wallet, mDL (ISO 18013-5), ID4Africa, and CARICOM wallet compatibility — external standards as an interop layer *around* FREK-ID, consistent with founder directive §8 ("External standards are interoperability mechanisms around FREK where appropriate... never replace FREK-ID").

## 2. The historical lifecycle: GENESIS → WORKSHOP → METAMORPHOSE → EMISSION → LEGACY

Per founder directive §4: this session found the lifecycle applied to **at least two different kinds of subject**, using identical stage names, in two different modules — this is the reconstruction required before any relocation decision, not yet a recommendation to merge or separate them.

- **`backend/frek_v1/` ("protocole identité Luciole", `memory/assurance_package_v1.0/01_Architecture_Overview.md:84`)**: the lifecycle of an **event-participant identity** (an OAuth2-client-scoped, email-attributable person minted for a specific event/context — `frek_v1/models.py:EmitRequest`). `GENESIS` = identity emitted (`EmitResponse.stage` default). Later stages recorded via explicit stage-transition calls (`STAGE_ORDER` dict, `frek_v1/models.py:17-22`) — this session did not find prose documentation of what specifically triggers `WORKSHOP`/`METAMORPHOSE`/`EMISSION` for this subject beyond the ordering itself; recorded as a gap, not invented.
- **`backend/frek/` ("FREK v2", NODE03, see `docs/architecture/FREK_LEGACY_ROUTE_AUDIT.md`)**: the lifecycle of a **creative work's certification** (an audio recording, identified by a triple-SHA-256 over its extracted frequency vector — a completely different subject than a person). `GENESIS` = intent declared before the work exists ("l'œuvre existe dans FREK avant d'exister dans le monde" — `routes.py:292`'s own docstring). `WORKSHOP` = a private, timestamped intermediate version added during creation. `METAMORPHOSE`/`EMISSION`/`LEGACY` exist in the enum but this session found no route in `backend/frek/` that transitions to them — only `/genesis` and `/workshop` are wired.
- **`backend/identity_engine/`**: no lifecycle at all currently (confirmed since Phase 1, re-confirmed every phase through this one) — WebAuthn registration/authentication ceremonies only, no stage concept.

**This is a third overload, distinct from Contradiction C1.** C1 is two systems (`frek_v1`, `identity_engine`) both minting *person* identities under the name FREK-ID. This finding is the *same five stage names* applied to a *work* in `frek/` versus a *person* in `frek_v1` — the vocabulary is shared, the subject is not. Per founder directive §12, this vocabulary is treated as potential conceptual IP (a deliberate metaphor — the "luciole"/firefly protocol name suggests a single light-emission lifecycle metaphor meant to apply broadly to anything FREK certifies, work or person alike) rather than something to rename away. Whether that is the founder's actual intent, or two independent designs that happened to reuse the same five words, is exactly the kind of question this document surfaces rather than silently resolves (§30: "If historical documents conflict with each other: document the contradiction. Do not silently choose.") — recorded as Contradiction C6 below.

## 4. Contradiction C6 (new) — DID typing: specified but not implemented

- **Source A**: `frek_v3/docs/FREK_Architecture_Integree_v0.2.md` §3.2 — four explicit typed DID subject kinds (`person-`, `org-`, `device-`, `app-`), `Statut: ARCHITECTURE VALIDÉE`.
- **Source B (code reality)**: `backend/did/document.py` — `did:frek:{frek_id}`, no type prefix, no distinction between a person's, an organization's, or a device's identifier.
- **Impact**: a consumer resolving `did:frek:<id>` today cannot tell from the DID alone what kind of subject it names — the architecture doc's own worked examples (a device issuing a hardware-signed capture credential vs. a person issuing an authorship credential) assume this distinction is resolvable from the identifier, which it currently is not.
- **Recommendation**: do not retrofit type prefixes onto already-minted `frek_id` values (would break every existing identifier, forbidden by founder directive §28). If type discrimination is wanted, it needs either a new, additively-versioned DID method variant, or a resolvable side-channel (the DID Document's own `@type` or a registry lookup) — a real design decision, not attempted here.
- **Founder decision required**: not urgent (no current consumer depends on type discrimination), but should be decided before any device-identity (Luciole/FAP) work begins, since that is exactly the case the architecture doc's own examples assume works.
